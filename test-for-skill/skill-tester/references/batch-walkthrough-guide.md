# 全量走查执行指南（Batch Walkthrough Guide）

本文档定义了 skill-tester「全量走查」模式的详细执行规范，确保任何人触发全量走查时都能以一致的方式执行场景级测试。

---

## 1. 走查范围定义

| 维度 | 默认范围 | 可选扩展 |
|------|---------|---------|
| 目标 | `skills/` 下所有含 `SKILL.md` 的子目录 | 用户可排除指定 Skill |
| 测试层级 | L0 + L1（规范校验 + 场景模拟执行） | 用户指定时可扩展至 L1.5（Fixture 写操作端到端） |
| 场景来源 | 每个 Scenario 取第一个 Prompt Example | — |
| 写操作处理 | 仅做逻辑校验（不实际写入） | L1.5 模式下实际执行（仅测试环境） |

---

## 2. 单 Skill 走查标准流程

对每个 Skill 执行以下步骤：

### 2.1 读取 Skill 定义

```
skills/<skill-name>/SKILL.md          → frontmatter + 模块定义 + 触发条件
skills/<skill-name>/references/*.md   → 场景定义（Scenario）
```

### 2.2 提取场景 Prompt 与预期行为

对 `references/` 中每个 `## Scenario N: <标题>` 块：

1. 找到 `**Prompt Examples**` / `**Prompt examples**` 段落，取**第一个** Prompt 作为测试输入
2. 找到 `**Expected Behavior**` / `**Expected behavior**` 段落，提取预期 MCP 工具调用链
3. 判断场景类型：
   - 含 `create_*_order` / `cancel_*` / `amend_*` / `set_*` / `update_*` 等写工具 → **写操作场景**
   - 其他 → **读操作场景**

### 2.3 模拟执行

以提取的 Prompt Example 作为「用户输入」，按 Skill 定义处理：

1. **意图识别**：Agent 判断用户意图，路由到正确模块
2. **工具调用**：
   - 读操作场景 → **实际调用 MCP 工具**，获取真实返回数据
   - 写操作场景 → **仅验证 Agent 构建的调用参数和确认流程**，不实际执行写入
3. **结果校验**：对比实际行为与 Expected Behavior

### 2.4 结果判定

按以下标准判定每个场景的结果：

| 结果 | 符号 | 判定标准 |
|------|------|---------|
| **PASS** | ✅ | MCP 工具调用链匹配预期 + 返回数据合理 + 写操作正确要求用户确认 |
| **PASS (注意)** | ⚠️ | 调用链正确但有注意点（如测试网数据为空、返回结构正常但无实际数据） |
| **PASS (逻辑校验)** | 📋 | 写操作场景：Agent 正确构建了调用参数、要求了用户确认，逻辑验证通过 |
| **FAIL** | ❌ | 调用链不匹配 / 关键参数错误 / 写操作跳过确认 / 路由到错误模块 |
| **BLOCKED** | 🔒 | 权限不足 / MCP 工具不可用 / 环境限制 / 生产环境写操作 |
| **SKIP** | ⏭ | 无 scenarios.md 且无子模块场景定义 |

### 2.5 记录摘要

每个场景的执行结果用 1-2 行文字记录关键数据，例如：
- `"BTC 100920.4 USDT, 5 档深度正常"`
- `"0.0001 BTC @ 95000, status=open"`
- `"taker:0.1%, maker:0.1%"`
- `"逻辑验证通过（sell+buy 两步）"`

---

## 3. FAIL 场景详细记录

当场景判定为 FAIL 时，必须额外记录 MCP 调用详情：

```markdown
- **MCP 调用详情**：
  - 工具：`{tool_name}`
  - 请求参数：
    ```json
    { ... }
    ```
  - 响应状态：{status_code}
  - 响应体：
    ```json
    { "label": "...", "message": "...", "data": ... }
    ```
```

PASS 场景仅在「实际数据摘要」列记录关键返回值，不展开完整响应。

---

## 4. 跳过规则

以下情况跳过该 Skill 或场景：

| 情况 | 处理方式 |
|------|---------|
| Skill 无 `references/` 目录 | 整个 Skill 标记 `SKIP (无场景定义)` |
| `references/` 中无 `## Scenario` 定义 | 整个 Skill 标记 `SKIP (无场景定义)` |
| Composite Skill（引用其他 Skill 的场景） | 走查其直接定义的场景，子模块场景在各自 Skill 中测试 |
| 场景的 Prompt Examples 为空 | 该场景标记 `SKIP (无 Prompt)` |
| 用户主动排除 | 标记 `SKIP (用户排除)` |

---

## 5. 分批策略

| 条件 | 建议 |
|------|------|
| 总场景数 ≤ 50 | 一个 Session 内完成 |
| 总场景数 51-150 | 分 2-3 个 Session，每 Session 走查 3-5 个 Skill |
| 总场景数 > 150 | 分 4+ Session，优先走查 P0 Skill（交易核心） |

分 Session 时的处理：
- 每个 Session 结束时生成临时报告 `all-skills-walkthrough-report-part-N.md`
- 最后一个 Session 合并所有临时报告为最终报告 `all-skills-walkthrough-report.md`
- 跨 Session 时在新 Session 开头说明续接信息（从哪个 Skill 继续）

### 6.2 格式规范

- 每个 Skill 一个独立的子表（`### 3.x <skill-name>`）
- 场景编号在 Skill 内部连续（1, 2, 3...）
- Fixture 列：无前置依赖写 `none`，有 Fixture 时标注类型（如 `open_order`、`batch_orders`）
- MCP 工具列使用反引号包裹工具名，关键参数用括号注明
- 结果列使用符号 + 文字（如 `✅ PASS`、`❌ FAIL`）
- 实际数据摘要控制在 1 行以内
- 每个 Skill 子表末尾附小结行

## 7. L1.5 扩展（可选）

当用户指定走查至 L1.5 时，写操作场景改为实际执行：

1. 按 SKILL.md 主文件中定义的 Fixture 机制自动构建前置状态
2. 实际调用写操作 MCP 工具
3. 校验结果
4. 执行 Teardown 清理

L1.5 扩展仅在以下条件同时满足时启用：
- 用户明确指定（如 `"全量走查到 L1.5"`）
- 环境检测为测试环境（Step 0.5）
- Fixture 状态为已启用

生产环境下 L1.5 写操作场景自动降级为 `🔒 BLOCKED (生产环境禁止写操作)`。
